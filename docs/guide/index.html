spec-as-truth

You decide what. The run decides how.

The spec is the source of truth and the code is the artifact. Shape the change, amend the spec, derive a plan from the delta, and run it — unattended if you like — until the pin moves. A question about behaviour parks its task. The run logs how it built the rest.

Install the plugin once, in Claude Code. Then run spec-init in the repo. It scaffolds specs/ and stops. A repo with no history continues as greenfield; a repo with history continues as brownfield. 

# once, in Claude Code
/plugin marketplace add stjarnstrom/spec-system
/plugin install spec-system@stjarnstrom

# then, in the repo
/spec-system:spec-init

The circuit

From idea to pin

Everything that needs you happens before the run: the interview, the plan, and spec-run’s readiness questions. After a two-line summary, the next thing you read is the report.

  1. spec-shape — interview, one question at a time
  2. spec-amend — statements become the spec and a plan
  3. plan — the work list in docs/changes/active/
  4. spec-run — implementer, reviewer, then the pin
  5. report — Blocked on me, Changed, Found, Rulings

A question about what the software does parks the task and returns to spec-shape.

Fig. 1 — shape and amend while you are here; the run continues alone

you, until the plan is settled the run: how, logged as rulings needs you: a parked question, then the report

Specs carry no version numbers. Git holds their history. The pin is a content hash of the spec file: equal to the file means in sync, different means an amendment awaits implementation, none means the code does not exist yet. The mismatch is the backlog.

The line

Who decides what

Observable behaviour is yours. How the code is built is the agent’s, recorded when another engineer could reasonably have gone the other way. A run never guesses what the software does.

MomentYouThe agent
spec-shape Purpose, behaviour, edge cases, test seams, what is out of scope — one question at a time, recommendation first Reads the code, the specs, the glossary, the ADRs. Looks up any fact the code can answer.
spec-amend Nothing new. It writes what you already approved. Allocates IDs, edits the spec, derives the plan. The pin stays where it is.
readiness Open questions, verification commands, a red baseline, the end state, permissions Collects every question the run would otherwise stop for, and asks them before it starts.
the run Nothing, until the report Decides how, logs each ruling, parks any question about what.
the report Answers under Blocked on me. A look at the rulings. Leads with what needs you.
Routing

What triggers what

Three things can start a skill. Name it, describe the situation in ordinary language, or let the session map do it. The skills then hand off to each other.

You name it

slash command

/spec-system:spec-shape interviews. /spec-system:spec-run executes outstanding plans. The same prefix covers init, adopt, amend, and the rest.

The session map

every session

At startup, after /clear, and after compaction, a hook injects a short skill map. “Let’s build…” routes to spec-shape. “Run it overnight” routes to spec-run.

The prompt hook

optional

With OPENROUTER_API_KEY set, and no run already in progress, each prompt is matched to a skill. A confident answer adds one line naming it. No key, a timeout, or a low-confidence answer adds nothing.

You say, or the repo looks likeSkillWhat it does
“let’s build”, “add a”, “make it”, “I want it to”, “should we” — behaviour not yet approved spec-shape Interviews, one question at a time. Writes no code and no spec.
Statements are approved, or anomaly findings should become spec changes spec-amend Edits the spec and derives the plan. Leaves the pin alone.
“run it”, “overnight”, “take it from here” — plans already exist spec-run Settles every remaining question, then runs the plans unattended.
A plan exists and you are staying in the session spec-implement The same per-task loop, without the walk-away wrapper.
Something is broken, failing, flaky, or slow debug A red loop first. Then a fix under the pin, or an amendment if the statement was wrong.
Structure is hard to change or test. Behaviour stays the same. architecture A standalone plan. spec-run executes it. archive closes it.
The repo has no specs/ spec-init Scaffolds the layer and stops for you. It adopts nothing.
Existing code, a capability you have confirmed spec-adopt Describes what the code does today and pins that description. Fixes nothing.

spec-shape classifies before it interviews. When it is unsure, it takes the heavier path. Complexity found midway moves the path up.

A question

stop

“Would this work?” becomes a prototype or a research note. The verdict can become a statement later.

Small and unowned

no spec

The flow already exists and no owned path is touched. A short design, one explicit yes, then test-driven development.

Behavioural

the interview

It changes what an owned capability does, adds a capability, or is big enough to want a plan. Then spec-amend.

Several capabilities

in order

One amendment per capability, in dependency order. Shape each in turn.

spec-run will not invent a plan. A feature with no plan goes back to spec-shape.

Two situations

Look at the repo

The size of the idea does not choose the walk. The state of specs/ does. spec-init forks internally: a repo with no real history is greenfield; a repo with history is brownfield.

What you findStart here
No specs/ yet /spec-system:spec-init
A capability is unspecified and the code exists /spec-system:spec-adopt — describe it before you change it
A capability is pinned and you want different behaviour /spec-system:spec-shape, then spec-amend
registry.mjs check reports an amendment outstanding, or a plan sits in docs/changes/active/ /spec-system:spec-run to leave, or spec-implement to stay
Walk one

Greenfield

No history for co-change to read, and nothing for spec-adopt to describe. The first spec is a target. pinned: none is the record that the code does not exist yet.

Scaffold, then stop

spec-init copies the registry, FORMAT.md, and a pre-commit hook into specs/, and appends a short section to the repo’s agent instructions. It fills the verification commands — test, typecheck, lint — from the manifest. With no history it skips the boundary proposal. The first capability is named in the interview, and its status stays unspecified until the first pin.

Interview for the capability

Describe what you want, or run /spec-system:spec-shape. One question per message, recommendation first. You name the capability. Facts come from whatever code exists; decisions come from you.

Approve a target spec

The design is presented in sections: statements, test seams and constraints, what is out of scope. Each approval covers the section shown. spec-amend writes the target with pinned: none and a plan in docs/changes/active/. While the pin is none, check notes owned paths that are not on disk yet.

Run it

/spec-system:spec-run. Answer the readiness questions. Each task’s test must fail at the starting commit, then go green. The last act is node specs/registry.mjs pin <capability>: the hash matches the file, the plan moves to docs/changes/completed/, and status becomes adopted.

Later features on that repo are the ordinary loop. The pin mismatch is the outstanding work.

Walk two

Brownfield

The code already exists. The first job is to describe it truthfully, then change it spec-first. A pin that lies at birth makes every later drift check worthless, so adoption changes no product code.

Propose boundaries, then you draw them

/spec-system:spec-init scaffolds the same substrate, then clusters git history (cochange.py, about 24 months). Proposed capabilities, seams, and edges enter the registry as status: unspecified. You confirm which lines to keep. Nothing is adopted in that pass. Later, /spec-system:spec-boundaries is the same proposal when the code has moved on.

Adopt one capability as it is

Start with the smallest confirmed capability that has real tests. /spec-system:spec-adopt reads the owned paths and the tests that touch them, and writes statements of what the code does today — ugly behaviour included. Existing tests become verified-by. Where nothing covers a requirement, the statement stays UNVERIFIED. Everything unjustified goes on specs/<slug>.anomalies.md. Then it pins: the hash says the code satisfies this description right now.

Turn a wish into a delta

Wishes live on the anomaly list. Most of them never become requirements. A change to what an adopted capability does starts at spec-shape. Approved statements go to spec-amend, which leaves the pin where it is. New behaviour gets a new id: a verified statement is split, so its evidence stays attached. An open -U- uncertainty is a hard stop until you answer it.

Run the delta

spec-run implements the plan. When every task is done and the suite is green, the pin moves. Anything parked is partial delivery: the pin stays, and the plan stays in active/.

A bug does not automatically start spec-shape. /spec-system:debug builds a red loop, then checks the pinned statements. When a statement already requires the correct behaviour, the fix is a regression test under the pin. When the statement itself was wrong, that is an amendment.

Walk away

Anatomy of a run

spec-run takes the plans you named, or every outstanding one: capabilities whose spec differs from the pin, and standalone plans in docs/changes/active/. A plan whose capability depends on another outstanding capability runs after it.

before

Readiness

One question at a time, recommended answer first. Open -U- questions a task depends on — answer now, or accept that the task parks. [human] tasks. The verification commands, and a baseline run of the suite. A red baseline is your call: fix it first, or run anyway with those failures recorded as pre-existing.

end state · permissions · then a two-line summary

isolate

A worktree, then the ledger

On the default branch the run works in a worktree (.worktrees/<run-name>, branch spec-run/<run-name>). Already on a feature branch, it stays there. Dependencies install from the lockfile. run.mjs active set marks the run so a later session can resume from the plan and git log.

end state: leave the branch · merge locally · push and open a PR

each task

Implementer, then reviewer

A fresh implementer writes the task test-first from a brief: the statements verbatim, the owned paths, the test seam. A reviewer judges the diff against those statement ids and for quality. A task is ticked only when every statement it names is SATISFIED and the tests are green. Fix rounds stop at five. A statement still missing is never ruled away.

how → a ruling in the plan’s run log · what → park that task

last

The pin moves

After a final review and a fresh run of check, the suite, typecheck, and lint. registry.mjs pin records the spec file’s hash and moves the plan to completed/. A standalone plan — one that changes no spec — is closed with archive instead.

anything parked → the pin stays

back

The report

Integration follows the end state you chose. Pushing and opening a pull request happen only on an explicit yes. Then the scratch directory .spec-run/ is removed. Git and the plans are the record.

Blocked on me · Changed · Found · Rulings

Coming back

Blocked on me

answer these

Parked tasks, each with a one-line question. Answer them. spec-amend folds each answer into the spec, rewrites the task, and unparks it. Run spec-run again.

Changed

what landed

Per plan: whether the pin moved, the statements now true, the verified count, and where the work is — branch, pull request, or merge.

Found

left on the list

Anomalies, deferred minor review findings, and friction worth a later fix. A rule the reviewer enforced by hand more than once is a candidate invariant.

Rulings

how it was built

Every implementation decision, with what it costs if wrong. They also stay in the plan’s run log after the plan moves to completed/.

A run stops early only for an irreversible or destructive operation, a security-sensitive action, a side effect outside the repository you did not authorise, or every remaining task parked. A behaviour question parks one task. A red test is more work.

The backlog

The pin

specs/registry.yaml records, per capability, the hash of the spec file the code satisfies. Specs have no version numbers. Equal, different, or none is the whole status.

Equal

in sync

The file hash matches pinned. No outstanding amendment. check is quiet about this capability.

Different

amendment outstanding

Someone edited the spec and left the pin. check demands a plan:. That plan is the work list.

none

code does not exist yet

A greenfield target. check notes owned paths that are not on disk. The first successful run replaces none with the file’s hash.

# the mismatch is the backlog
node specs/registry.mjs check

# which capability owns these files
node specs/registry.mjs owns path/to/file.ts

# last act of a finished plan — moves the pin, archives the plan
node specs/registry.mjs pin <capability>

Statement ids are permanent: requirements PREFIX-NNN, invariants PREFIX-I-NNN, uncertainties PREFIX-U-NNN. Withdrawn statements keep their heading. Ids are never renumbered and never reused.

Where a run lives on disk

PathWhat it is
specs/<slug>.md The capability, present tense. No history, no rationale.
specs/<slug>.anomalies.md What the code does that nothing justifies. The input to a later amendment.
specs/registry.yaml Capabilities, owned paths, the pin, dependency edges, seams.
docs/changes/active/ Outstanding plans. The run log inside each plan is the ledger.
docs/changes/completed/ Plans whose pin has moved, or standalone plans that were archived.
docs/adr/ Rationale, when a decision is hard to reverse, surprising, and a real trade-off.
.spec-run/ Scratch for one run: briefs, reports, diffs. Removed when the run ends.
When it feels wrong

Field notes

The skills stop on purpose at a few places. Each one is a question only you can answer, or a rule that keeps the pin honest.

What you seeWhat it meansWhat you do
You said “let’s build” and code started appearing The change was classified as small and unowned, or no skill was named Invoke /spec-system:spec-shape. When the work is bigger than a one-yes design, the interview writes a plan before any product code.
/spec-run points you at spec-shape There is no plan yet. The run executes plans. Finish the interview and the amendment. Then run.
A task is parked A question about observable behaviour came up, or an open -U- was left for later Answer it. spec-amend folds the answer into the spec and unparks the task. The next spec-run picks it up. Any commits sit on spec-run/parked-<T>.
The pin did not move Partial delivery. Something is still parked, or the suite was red. Read Blocked on me. The plan stays in docs/changes/active/. The file/pin mismatch is the record.
The suite was already red Readiness ran the tests on the starting commit Fix the baseline first, or tell the run to continue and record those failures as pre-existing.
The run is sitting on a permission prompt The session cannot edit files or run the verification commands unprompted Switch to auto mode, or add allow rules for those commands. The run does not change permission settings itself.
Adoption started fixing the code The pin would describe a wish, and every later drift check would be worthless Keep the product diff empty. Wishes belong on *.anomalies.md. Desired behaviour is the next amendment.
A verified statement grew a new clause Widening detaches its evidence. The old test still passes and now proves less than the spec claims. Leave the verified statement under its id. Put the new behaviour in the next free id.
You want to change the software mid-run A change to how is a ruling. A change to what is a spec change. Send it. The run parks the affected tasks, spec-amend takes the change, and the tasks resume.
A session starts and a run is already marked active Compaction, or a new session, during a run Leave it. spec-run resumes from run.mjs status and the plan’s checkboxes. It does not restart.

Other doors

debug

a bug

A red feedback loop before any theory. Then either a fix under the pin, with the regression test as verified-by, or an amendment when the statement was wrong.

architecture

structure

Ranks deepening candidates and writes a standalone plan (capability: none). spec-run executes it. archive closes it. No pin moves.

review

a branch or PR

Spec and standards in separate passes. Comments you received are the same skill’s second half.

finish

after the run

Verify, then merge locally, push and open a pull request, or keep the branch. Worktrees are removed only when git agrees they are clean.
